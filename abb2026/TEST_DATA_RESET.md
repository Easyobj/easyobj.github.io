# 发布前测试与用户数据清理（V5.9.28）

## 测试日期误配后的维护恢复

发布时间已过且已有测试中奖记录时，“已有记录不能改期”和“正式开始后不能清理”会同时生效。不要删除日期锁或直接改数据库日期来绕过保护。

V5.9.28 增加受控恢复：服务器管理员先确认今年库中全部为测试数据，再在私密配置签发 **限时、针对原始精确发布时间、只可使用一次** 的恢复授权。恢复不会自动清理或恢复库存；无授权的正式活动仍不能清理。授权不能从网页勾选、URL 或 POST 设置，过期后失效，成功后审计中的授权标识不可重复使用。

使用顺序：

1. 在“活动设置”暂停新增抽奖。
2. 打开“测试数据清理”。在已授权恢复状态下，必须填写新的未来正式发布时间（页面注明活动时区）。
3. 勾选全部为测试用户，输入“清空全部测试用户”和当前管理员密码。
4. 默认不要勾选恢复库存。仅确认没有实际发出礼品才选库存恢复。
5. 点击提交后先自动完整备份；七个用户表清理、未来发布时间保存和审计同一事务提交，任一步失败回滚。抽奖仍保持暂停，后续由运营员恢复测试。

正常发布前测试期间也可选填新发布时间，一次完成清理与重新排期；不填则保留原时间。临时授权只针对已确认误配的旧时间，不提供通用“正式期可删除”开关。恢复后自动进入新时间之前的常规测试阶段，到新发布时间后清理再次关闭。

服务器私密授权配置结构为 `testing.schedule_recovery`，字段包括严格布尔 `enabled`、随机 32 位十六进制 `id`、匹配当前配置的 `expected_starts_at`、显式 UTC 的 `expires_at`。由授权服务器管理员填写；不要复制示例占位符作为有效授权，也不要提交实际私密配置。程序确认过期/已消费授权不会再生效。

本轮用户确认当前正式库两位用户及一条已核销中奖均为测试数据，允许启用一次恢复入口；不代表允许代理点击清理或回补库存。

运营员在“活动设置”中设置站点业务时区下的正式发布时间，并勾选“发布前允许测试与测试数据清理”。开始前用户可以授权、答题、抽奖及现场核验；到发布时间自动转为正式活动，清理入口自动禁用。正式活动只在连续前四个自然日发奖。

旧版只有日期配置时，原首次转为未来发布时间的确认逻辑保留。已有精确发布时间且已有中奖记录时，不能直接更改发布时间重开活动；本轮增加上方有明确授权的“先备份、清理并重新排期”事务流程。

## 清理流程

1. 运营员先暂停新增抽奖，确认当前全部用户都是测试用户。
2. 进入“测试数据清理”，核对数量，输入“清空全部测试用户”和当前管理员密码。
3. 每次操作先自动创建整个今年数据库的完整、受 PHP guard 保护的私密备份；验证备份成功后，事务删除七个用户侧关联表。备份或审计失败不提交删除。
4. 账号、密码、活动配置、审计、奖品配置保留；默认不回补库存。仅确认测试没有实际发出礼品时，才额外勾选恢复测试库存和未实际发奖确认。
5. 清理后测试用户重新授权即可重新答题和抽奖；不重置自增 ID，不删除 Runtime。

清理仅运营员可用，核验员不可访问或执行。保护数据/库存快照，页面打开后发生变化时要求刷新。开始前应用请求参与数据库维护锁；清理事务在备份前、删除前和提交前重新检查发布时间，正式开始后禁止提交清理。

## 服务器要求

已有数据库先备份，执行 `api/database/migrations/2026_10_06_publication_testing.sql`；部署流程检查列/索引存在性，避免重复 ALTER。新建备份目录 `Application/Runtime/test-data-backups/`，实际 PHP 用户所有、0700，备份 PHP 文件0600。不要将备份放入 Git、Pages 或公共上传包。

备份编号显示在操作结果和审计中，不提供公开网页下载。授权服务器管理员可使用 `api/bin/export-test-backup.php` 导出 guarded SQL 后按独立恢复流程处理。应用不自动执行清理，部署也不会删除现有用户或中奖记录。
